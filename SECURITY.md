# Security Policy

## Supported versions

| Version | Supported |
|---------|-----------|
| 2.0.x (current release 2.0.1) | yes |
| < 2.0   | no |

Fixes land on the current minor line only. If you are running an older release,
upgrade before reporting a problem against it.

## Reporting a vulnerability

**Use GitHub's private security advisory form.** It opens a private thread between you
and the repository administrators — no email address, mailing list, or account on a
third-party service is needed:

<https://github.com/myzticalbabe/grantforge/security/advisories/new>

(The **Report a vulnerability** button on the repository's *Security* tab leads to the
same form.)

Do **not** open a public issue for a security problem. A public issue is visible to
everyone the moment it is filed, and it cannot be edited away after the fact.

### What to include

- the affected version (`python -m grantforge version`) or commit;
- what an attacker could do, and what they need in order to do it;
- steps to reproduce, or a proof-of-concept;
- the full error output or traceback.

### What happens next

- You will get an acknowledgement. The maintainer works on a best-effort basis and
  aims to acknowledge a report within seven days.
- The report is discussed in the private advisory until a fix is ready.
- You are credited in the advisory unless you ask not to be.
- Please give the maintainers a reasonable window to publish a fix before disclosing
  publicly.

## What is in scope

GrantForge reads RFPs and proposal documents, writes proposal drafts, and exports
PDF, Word and Excel files. Reports that are useful here include path traversal or
command injection in file handling, unsafe parsing of a supplied RFP or proposal
file, and credentials or API keys written into exported files.

## Out of scope

- The absence of a `submit` command, or the fact that the engines are deterministic
  and rule-based rather than model-backed. Those are design decisions, not
  vulnerabilities — see the [README](README.md) for what the project actually does.
- Vulnerabilities in the upstream dependencies themselves. Those are reported to the
  upstream projects; `pip-audit` and Dependabot will surface them here.
- Reports generated by an automated scanner with no demonstrated impact.

## Other channels

Non-security bugs go to the issue tracker using the **Bug report** template.
Behaviour that is unacceptable but not a vulnerability goes to the channels in
[CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md).
